## Why deploy with a container image?

When an environment doesn't set the `deployment` option, Ymir deploys it to AWS Lambda as a zip archive. AWS Lambda limits a zip archive deployment to 250MB uncompressed, and that limit also counts Lambda layers such as the PHP runtime. On top of that, the Ymir CLI stops the build if the files in the zip archive add up to 147,005,412 bytes or more uncompressed. (This excludes uploads which aren't stored on AWS Lambda.) For larger sites, this limit can prevent your project from being deployed with Ymir. However, if you deploy using a container image, AWS Lambda allows an image of up to 10GB uncompressed, including all its layers.

Another reason to use a container image is so you can install other PHP extension and libraries which aren't available with the default Ymir runtime.

With container image deployment, the zip archive rules that only keep certain files don't apply. Your `Dockerfile` decides what goes into the image, and the Dockerfile generated by the Ymir CLI copies the entire [build directory][4] into the image. You can use a `.dockerignore` file or the `exclude` build option to keep files out of the image.

## Requirements

Container image deployment uses [Docker][1] or [Podman][5] to build your container image and push it to your AWS infrastructure. The Ymir CLI uses Podman if it's installed and Docker otherwise. It builds the image on the machine that runs the `build` or `deploy` command, and the `deploy` command then pushes it from that machine.

The Ymir CLI builds the image for the Linux architecture configured for the environment with the [`architecture`][6] option. That's `linux/arm64` for `arm64` and `linux/amd64` for `x86_64`. Environments without an `architecture` option use `x86_64`. If your `Dockerfile` has `RUN` instructions, such as ones that install PHP extensions, building on a machine with a different architecture requires [emulation][7] and is much slower. Building on a machine with the same architecture as the environment avoids this.

When deploying, Ymir creates your project's Amazon ECR repository if needed and gives the Ymir CLI temporary credentials to push the image to it.

## Creating a new project with container image deployment

Creating a new project with container image deployment is a breeze. You simply have to create a project normally using the `ymir init` command. Towards the end of the project creation process, you'll get asked if you want to use container image deployment. That's it!

If you answer yes, the Ymir CLI creates a project-wide `Dockerfile` for the `arm64` architecture and your project type's default PHP version. It asks before overwriting an existing `Dockerfile`. It also configures every environment it creates for the new project to use container image deployment.

## Switching an existing environment to container image deployment

<Callout type="error" title="Cannot rollback after switching">

Once you switch to using container image deployment, you won't be able to rollback to a deployment that used zip archive deployment. Prior deployments will still be visible so you can see your deployment history. But trying to rollback to them will cause an error. The same applies if you switch an environment back to zip archive deployment.

</Callout>

Switching an existing environment doesn't happen automatically. You switch each environment by giving it a `Dockerfile` and changing its configuration. The first container image deployment replaces the environment's AWS Lambda functions. This is why you can't rollback to the zip archive deployments.

### Creating the Dockerfile [#creating-the-dockerfile]

First, you'll need to create a `Dockerfile` to use for your project. You can create one using the [`docker:create`][2] command. When you pass the environment name, the command creates a Dockerfile only used by that environment.

```bash
ymir docker:create staging
```

This creates a `staging.Dockerfile` file using the `architecture` and `php` options of the `staging` environment. If the environment doesn't have one of these options, pass the value with the `--architecture` or `--php` option.

```bash
ymir docker:create staging --architecture=x86_64 --php=8.3
```

Without an environment name, the `docker:create` command creates a project-wide `Dockerfile` for the `arm64` architecture, unless you use the `--architecture` option. When building an environment, the Ymir CLI uses the environment's Dockerfile, such as `staging.Dockerfile`, if it exists and the project-wide `Dockerfile` otherwise.

Keep the following in mind when using your Dockerfile:

* Use the `ymirapp/arm-php-runtime` image for the `arm64` architecture and the `ymirapp/php-runtime` image for the `x86_64` architecture. When you deploy or run the `validate` command, the Ymir CLI rejects a Dockerfile that uses the runtime image or `FROM --platform` value for the other architecture. It doesn't check whether other base images are compatible.
* The PHP version comes from the runtime image tag in the Dockerfile, such as `php-83`. Ymir ignores the environment's [`php`][8] option with container image deployment.
* The Dockerfile needs to be in the project directory when you build. If your `.gitignore` file ignores it, add it using the `include` build option.

### Configuring the environment [#configuring-the-environment]

Next, you'll need to edit your `ymir.yml` configuration file. In it, you'll want to add the [`deployment`][3] option and set it to `image`. Below is an example of an `ymir.yml` file where the `staging` environment is configured to use container image deployment.

```yml
id: 42
name: container-project
type: wordpress
environments:
  production: ~
  staging:
    cdn:
      caching: assets
    cron: false
    deployment: image
    warmup: false
```

The `docker:create` command can also make this change for you. It asks you after creating the Dockerfile, or you can use the `--configure-project` option. This sets the `deployment` option to `image` and removes the `php` option.

```bash
ymir docker:create staging --configure-project
```

<Callout type="warn" title="Configuring every environment">

If you don't pass an environment name, the `--configure-project` option configures every environment in your `ymir.yml` file to use container image deployment.

</Callout>

The `--configure-project` option replaces the whole `deployment` option. If the environment uses the `deployment` option to configure deployment `commands`, set the `type` yourself instead so you keep them.

```yml
environments:
  staging:
    deployment:
      type: image
      commands:
        - 'wp cache flush'
```

Once the environment is configured, you deploy it like any other environment.

```bash
ymir deploy staging
```
