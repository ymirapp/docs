## Starting the deployment process

To begin a new deployment to a project environment, you use the `deploy` command.

```bash
ymir deploy
ymir deploy environment-name
```

If you don't specify an environment, the `deploy` command asks you to choose the environment to deploy to. You must specify the environment as an argument, as shown above, when running the `deploy` command in non-interactive mode.

The `deploy` command validates your `ymir.yml` file with Ymir, builds the project for the environment, uploads the build to your AWS infrastructure and then starts the deployment. When the environment uses [container image deployment][3], uploading the build means pushing the container image to your project's Amazon ECR repository.

## Build process

Deploying a project to an environment starts with the build process. This is where Ymir CLI creates a build artifact for AWS Lambda and also separates your project assets to upload them to S3 if needed. The whole process happens in the `.ymir` temporary directory where the Ymir CLI will create a copy of your project. You can also test the build process using the `build` command.

```bash
ymir build environment-name
```

The `build` command doesn't deploy anything, but it still needs to authenticate with Ymir to find the project environment.

### What gets copied [#what-gets-copied]

The build doesn't use your project directory as is. The Ymir CLI copies your project files to `.ymir/build` first, and every later build step works on that copy. When copying your project files:

* If your project has a `.gitignore` file, the Ymir CLI doesn't copy files that Git ignores. This includes directories such as `vendor` or `node_modules` if your `.gitignore` file lists them. Files that aren't ignored are copied even if you haven't committed them.
* The Ymir CLI doesn't copy hidden files or directories, such as `.git` or `.env`. It also doesn't copy your `ymir.yml` file or, for WordPress, Bedrock and Radicle projects, the uploads directory.
* Some project types add files back. WordPress projects always copy `wp-config.php` if it exists, and Laravel projects copy their `.env` files except `.env.example`.
* You can copy additional paths, including ignored ones, using the [`include`][4] build option.

After running your build commands, the Ymir CLI removes `.git` and `node_modules` directories as well as `.ts`, `.tsx` and `.scss` files from the build. Laravel projects also remove paths such as `storage` and `tests`. It also removes any paths listed in the `exclude` build option. Paths listed in the `include` build option override these exclusions, but project types can remove other paths during cleanup. For example, Laravel projects can still remove included `storage` or `tests` paths. If you include a special path, [inspect the build][8] in `.ymir/build` to check that it's there.

The build then extracts asset files, which are the files your project serves to browsers such as images, CSS and JavaScript, so that the deployment can upload them to S3. What goes into the build artifact depends on the environment's deployment type:

* **Zip archive:** For WordPress, Bedrock and Radicle projects, the archive only contains PHP files, `.mo` translation files, WordPress core directories and the few theme and plugin files WordPress needs to read on the server. Laravel archives aren't filtered by file type. Paths listed in the `include` build option are also added to the archive.
* **Container image:** Your `Dockerfile` decides what goes into the image. The Dockerfile generated by the Ymir CLI copies the entire build directory into the image.

### Build commands [#build-commands]

Ymir also lets you add your own build steps to the process. You do that by adding them to the `build` option of your project's `ymir.yml` configuration file. Below is an example where the Ymir CLI would run `yarn install` and `yarn build` during the build process.

```yml
id: 1
name: project-name
type: wordpress
environments:
  environment-name:
    build:
      - 'yarn install && yarn build'
```

The Ymir CLI runs build commands in the `.ymir/build` directory. Because ignored files such as `vendor` or `node_modules` aren't copied there, build commands that need your project dependencies must install them first. When you create a Bedrock, Radicle or Laravel project, Ymir adds a `composer install` build command for this reason. A WordPress project doesn't need Composer or Node.js unless your own build commands use them.

If you also want to use the `include` or `exclude` build options, put your build commands under the [`commands`][5] build option.

```yml
id: 1
name: project-name
type: wordpress
environments:
  environment-name:
    build:
      commands:
        - 'yarn install && yarn build'
      include:
        - wp-content/themes/my-theme/dist
```

<Callout type="warn" title="Build runs locally">

The build process runs on the machine that executed the `deploy` or `build` command. All the required tools to perform your build steps must be available for the build to work. This includes the PHP version used by any `composer` build command, which is the PHP installed on that machine and not the `php` version configured for your environment. Container image builds also require Docker or Podman.

</Callout>

## Redeploying a project

You can redeploy your project to an environment using the `redeploy` command. This is useful when you've made changes to [environment variables][1] or [secrets][2].

```bash
ymir redeploy
ymir redeploy environment-name
```

A redeploy doesn't build your project again. It reuses the build and the `ymir.yml` configuration saved with the environment's most recent deployment. Changes to your local project files or `ymir.yml` file aren't part of a redeploy. Use the `deploy` command for those.

The redeploy applies the environment's current environment variables and secrets, and it runs the [deployment commands][7] saved with the deployment again. It doesn't remove secrets you've deleted since that deployment was made. Use the `deploy` command to deploy without them.

<Callout type="warn" title="Most recent deployment">

The `redeploy` command uses the environment's most recent deployment even if that deployment failed. To return to an earlier working deployment, use the `rollback` command instead.

</Callout>

## Rolling back a deployment

It's also possible to rollback your project environment to a previous a deployment. You do this using the `rollback` command.

```bash
ymir rollback
ymir rollback environment-name
```

A rollback doesn't build or redeploy your project code. It points the environment back to the AWS Lambda function versions of a previous successful deployment and reapplies that deployment's saved configuration. It doesn't run that deployment's [deployment commands][7] again.

<Callout type="warn" title="Environment variables and secrets">

Rolling back an environment also rolls back its environment variables to the ones saved with the deployment you roll back to. It doesn't restore secret values. The rollback reuses that deployment's secrets, and redeploying a deployment overwrites them with the environment's current secrets. So a rollback can use newer secret values than the ones in place when the deployment was made.

</Callout>

A rollback doesn't change the environment's current environment variables and secrets, so your next `deploy` or `redeploy` uses them again. If a rolled back environment needs different secret values, change the secrets and redeploy.

If you want to select the deployment to rollback to, you want to use the `--select` option with the `rollback` command. If you don't use the `--select` option, the `rollback` command will rollback the environment to the successful deployment before the most recent successful one. Redeploys and rollbacks count as deployments, so running `rollback` right after a rollback returns the environment to the deployment you rolled back from.

```bash
ymir rollback --select
ymir rollback environment-name --select
```

<Callout type="warn" title="Not a data recovery tool">

A rollback only affects your project code and its deployment configuration. It doesn't restore your database, uploaded media or anything else your project changed while it ran. You also can't rollback to a deployment made before the environment changed its [deployment type][6].

</Callout>

## Troubleshooting a deployment [#troubleshooting]

When the `deploy` command fails, find out where it stopped before you run `deploy`, `redeploy` or `rollback` again. Each of them starts a new deployment that changes your environment.

* **The build failed:** The error happened on your machine before the Ymir CLI uploaded anything or started a deployment. Fix the build and [inspect it][8] if needed.
* **Ymir reported a failed deployment:** The command prints `Deployment failed` followed by the error message, such as the deployment command that failed and its output. The steps that finished before the failure aren't undone.
* **The command stopped waiting:** The error `Timeout waiting for deployment to terminate` only means that the Ymir CLI stopped waiting. It didn't cancel the deployment, which can still be running.

If a deployment started or you're not sure whether it did, check its status on the project page of the Ymir dashboard. Make sure that you're looking at this deployment and not an earlier one. Then check the logs of the relevant environment function with [`environment:logs:query`][9]. Use the `console` function for deployment commands and the `website` function for web requests. A deployment shown as **Timed out** only had its status changed. That doesn't prove that the work on AWS stopped.

If PHP on your machine has the `pcntl` extension, pressing `Ctrl+C` while the `deploy` command waits for the deployment asks Ymir to cancel it. Without `pcntl`, `Ctrl+C` only stops the Ymir CLI and doesn't ask Ymir to cancel anything. If the cancellation request fails, Ymir may or may not have received it, so check the deployment's status on the dashboard. Cancelling doesn't stop or undo a step that's already running.

If the deployment failed and you want the environment back on an earlier working deployment, use [`rollback`][10]. Don't use `redeploy`, which reuses the failed deployment.

### Inspecting a build [#inspecting-a-build]

The Ymir CLI deletes the `.ymir` directory when the command ends, even if it failed. To inspect the build, use the `--debug` option. It pauses the build until you press `Enter`.

```bash
ymir build staging --debug
```

While the build is paused, inspect `.ymir/build` from another terminal. The pause happens after your build commands and the cleanup, but before the Ymir CLI creates the zip archive or container image. So it doesn't show you exactly what goes into the archive or image. The `deploy` command has the same pause with its `--debug-build` option.
