This reference documents every command available in [Ymir’s command-line tool][6].

<Callout type="info" title="Selecting an environment">

No command defaults to the `staging` environment. If you don't pass an environment to a command that needs one, whether as the `environment` argument or with the `--environment` option, the Ymir CLI asks you to choose one of the project's environments. In non-interactive mode (`-n` or `--no-interaction`), there is no prompt, so you must pass the environment explicitly or the command fails.

</Callout>

## Login

```bash
ymir login
```

Authenticate with Ymir by logging in using your email, password and 2FA code (if enabled). Creates an authentication token locally.

<Callout type="info" title="Authenticate using an environment variable">

The Ymir CLI also lets you authenticate by storing an API token in the `YMIR_API_TOKEN` environment variable. You can create an API token on the [account management page][1].

</Callout>

<Callout type="info" title="Configuration file">

All the Ymir CLI configuration options (including authentication token) are stored in `~/.ymir/config.json`.

</Callout>

### certificate:request [#certificate-request]

```bash
ymir certificate:request [options] [<domains>...]
```

Request a new SSL certificate from the cloud provider.

<Callout type="warn" title="Add DNS records before deploying">

When requesting a certificate for a domain that isn't managed by Ymir, add the DNS records that the command displays right away and keep them in place. You can't deploy until the certificate is issued. Use [`certificate:info`][13] to display the DNS records again and [`certificate:list`][14] to check the status. See the [SSL certificates documentation][15] for more information.

</Callout>

#### Arguments [#arguments-7]

##### `domains` [#domains-optional]

**optional**

Space-separated list of domains that the SSL certificate is for. Wrap wildcard domains in single quotes. If you only pass one domain, the command asks if the certificate should also cover its wildcard domain. If you only pass one wildcard domain, the command adds its base domain.

#### Options [#options-4]

##### `--provider=PROVIDER` [#provider-provider]

The ID of the cloud provider where the certificate will be created. Defaults to the project's cloud provider connection when run from a project directory.

##### `--region=REGION` [#region-region]

The cloud provider region where the certificate will be located. Defaults to the project region when run from a project directory.

#### Usage [#usage-9]

```bash
# Create a SSL certificate with prompt for domain and region
ymir certificate:request

# Create a SSL certificate for "example.com"
ymir certificate:request example.com

# Create a SSL certificate for "example.com" and "*.example.com"
ymir certificate:request example.com '*.example.com'

# Create a SSL certificate for "example.com" in "us-east-1" region
ymir certificate:request example.com --region=us-east-1
```

### database:export [#database-export]

```bash
ymir database:export [options] [<database>]
```

Export a database to a local SQL file.

<Callout type="info" title="See it in action">

Check out the [video](https://www.youtube.com/watch?v=H92ewqQcU_M).

</Callout>

<Callout type="warn" title="Database name required for private database servers">

If you want to use the `database:export` command to export a database from a private database server, you must specify the `database` argument.

</Callout>

The Ymir CLI saves the export in the current directory as `<database>_<date>.sql.gz`, or `<database>_<date>.sql` with `--compression=none`. It asks before overwriting a file with the same name. The file contains all the data in the database, so run the command from a private directory outside your project.

What the export contains depends on the database engine:

* **MySQL:** The tables and their data, views and triggers. The export drops each table before recreating it. It doesn't contain stored procedures, functions or events. It runs in a single transaction, which helps keep transactional tables, such as InnoDB tables, consistent with each other. It doesn't protect other tables or changes to the structure of tables during the export, and it doesn't make the export consistent with your uploads.
* **PostgreSQL:** The local `pg_dump` executable exports the database with statements that drop each object before recreating it. The export doesn't contain object ownership or privileges.

An export doesn't contain database users or their passwords. Check that the file isn't empty and that you can import it into a scratch database before you rely on it. The `database:import` command can't import the format this command uses for MySQL triggers, so restore an export with triggers using another MySQL client.

#### Arguments [#arguments-10]

##### `database` [#database-optional-3]

**optional**

The name of the database to export.

#### Options [#options-7]

##### `--compression=COMPRESSION` [#compression-compression-default-gzip]

**default**: `gzip`

The compression method to use when exporting the database (gzip or none).

##### `--server=SERVER` [#server-server-3]

The ID or name of the database server to export a database from.

##### `--user=USER` [#user-user]

The user used to connect to the database server.

##### `--password=PASSWORD` [#password-password]

The password of the user connecting to the database server. If you don't use this option, the Ymir CLI asks for the password without displaying it, which keeps it out of your shell history.

#### Usage [#usage-12]

```bash
# Export a database with prompt for database server, database name, database user and password
ymir database:export

# Export a database named "database-name" on the database server named "database-server" with a prompt for database user and password
ymir database:export database-name --server=database-server

# Export a database named "database-name" on the database server named "database-server" using the "database-user" database user with a prompt for the password
ymir database:export database-name --server=database-server --user=database-user
```

### database:import [#database-import]

```bash
ymir database:import [options] <filename> [<database>]
```

Import a local SQL backup to a database.

<Callout type="info" title="See it in action">

Check out the [video](https://www.youtube.com/watch?v=H92ewqQcU_M).

</Callout>

<Callout type="warn" title="Database name required for private database servers">

If you want to use the `database:import` command to import a database to a private database server, you must specify the `database` argument.

</Callout>

The database must already exist, since the command doesn't create it. Only import a file from a source you trust, exported from a compatible database engine and version. Keep it outside your project and public directories.

How the import runs depends on the database engine:

* **MySQL:** The Ymir CLI runs the statements itself using PHP's PDO extension and its MySQL driver, not the `mysql` client. It skips empty lines and lines starting with `--`, joins the other lines without line breaks and runs a statement when a line ends with `;`. It's meant for dump files, not as a full MySQL client. It doesn't support `DELIMITER` commands, so it can't import the stored procedures, functions or triggers of dumps that use them, including the triggers that `database:export` exports. It doesn't run a last statement that doesn't end with `;`, and it doesn't warn you about it.
* **PostgreSQL:** The local `psql` executable runs the file and stops at the first error.

<Callout type="warn" title="Imports aren't reversible">

The Ymir CLI doesn't wrap an import in a transaction. Your file can contain its own transactions, but on MySQL, statements that drop or create tables can't be rolled back. So if an import fails partway, some changes can remain in the database. Many exports, including those from `database:export`, drop and recreate each table they contain, and tables that aren't in the export stay. Import into an empty database that no running site uses, and make a backup before importing into one with data. After a failed import, find the cause before you do anything else. Don't assume that importing again is safe. If nothing uses the database, you can recreate it empty and import again. Otherwise, restore it from your backup.

</Callout>

For a private database server, the command opens its own SSH tunnel to the network's [bastion host][3] on local port `3305` for MySQL or `5433` for PostgreSQL. You need the `ssh` command, and the port must be free, so stop any `database:server:tunnel` command using it first.

#### Arguments [#arguments-11]

##### `filename`

The path to the local .sql or .sql.gz file.

##### `database` [#database-optional-4]

**optional**

The name of the database to import into.

#### Options [#options-8]

##### `--server=SERVER` [#server-server-4]

The ID or name of the database server to import a database to.

##### `--user=USER` [#user-user-2]

The user used to connect to the database server.

##### `--password=PASSWORD` [#password-password-2]

The password of the user connecting to the database server. If you don't use this option, the Ymir CLI asks for the password without displaying it, which keeps it out of your shell history.

#### Usage [#usage-13]

```bash
# Import a database with prompt for database server, database name, database user and password
ymir database:import ~/backups/backup.sql.gz

# Import a database named "database-name" on the database server named "database-server" with a prompt for database user and password
ymir database:import ~/backups/backup.sql.gz database-name --server=database-server

# Import a database named "database-name" on the database server named "database-server" using the "database-user" database user with a prompt for the password
ymir database:import ~/backups/backup.sql.gz database-name --server=database-server --user=database-user
```

### database:server:create [#database-server-create]

```bash
ymir database:server:create [options] [<name>]
```

Create a new database server.

#### Arguments [#arguments-13]

##### `name` [#name-optional-2]

**optional**

The name of the database server.

#### Options [#options-9]

##### `--engine=ENGINE` [#engine-engine]

The database server engine to create (mysql or postgresql).

##### `--network=NETWORK` [#network-network-2]

The ID or name of the network on which the database will be created.

##### `--private` [#private]

The created database server won't be publicly accessible.

##### `--public` [#public]

The created database server will be publicly accessible.

##### `--serverless` [#serverless]

Create an Aurora serverless database cluster for the selected database engine.

This creates an `aurora-mysql` cluster when `--engine=mysql` is selected and an `aurora-postgresql` cluster when `--engine=postgresql` is selected. Serverless database clusters are private, can't be created using the `--public` option, and don't use the `--storage` option.

##### `--storage=STORAGE` [#storage-storage]

The maximum amount of storage (in GB) allocated to the database server.

For database servers that aren't Aurora clusters, the Ymir CLI asks for the storage and suggests `50` if you don't use this option. In non-interactive mode, the storage falls back to `50`. The `--storage` option doesn't apply to Aurora or serverless database clusters.

##### `--type=TYPE` [#type-type-3]

The database server type to create on the cloud provider.

#### Usage [#usage-15]

```bash
# Create a new database server with prompts for the name, network, database engine, serverless, type, storage and public access
ymir database:server:create

# Create a PostgreSQL database server named "database-server"
ymir database:server:create database-server --engine=postgresql --network=network --type=db.t3.micro --storage=50 --public

# Create an Aurora Serverless PostgreSQL database cluster with prompts for the name and network
ymir database:server:create --engine=postgresql --serverless
```

## DNS

Commands to manage your DNS records and zones.

### dns:record:change [#dns-record-change]

```bash
ymir dns:record:change <zone> <type> <name> <value>
```

Change the value of a DNS record.

<Callout type="info" title="Use comma-separated values to create multiple DNS records">

To create multiple DNS records for the name and type (for example with MX records), you want to use commas to separate each value to add as a record. Please check the usage section below for an example. Ymir always splits values on commas, so you can't create a value that contains a comma.

</Callout>

<Callout type="warn" title="Overwrites existing DNS record">

The `dns:record:change` command will overwrite an existing DNS record if one already exists with the same name and type. It replaces all the record's values, including for records that Ymir manages, such as SSL certificate validation records. Save the current values before you change a record.

</Callout>

Ymir saves the record and then applies the change to Route 53 in the background. The command's success message doesn't confirm that Route 53 applied it. Query the DNS zone's name servers to check.

#### Arguments [#arguments-25]

##### `zone`

The ID or name of the DNS zone that the DNS record belongs to.

##### `type`

The DNS record type. The supported types are `A`, `AAAA`, `CAA`, `CNAME`, `MX`, `NAPTR`, `NS`, `PTR`, `SOA`, `SPF`, `SRV` and `TXT`.

##### `name`

The name of the DNS record without the domain. Use `@` for the root of the domain.

##### `value`

The value of the DNS record.

#### Usage [#usage-28]

```bash
# Change the A record of "example.com" to 192.0.2.10
ymir dns:record:change example.com a @ 192.0.2.10

# Change the A record of "subdomain.example.com" to 192.0.2.10
ymir dns:record:change example.com a subdomain 192.0.2.10

# Change the MX records of "example.com"
ymir dns:record:change example.com MX @ "10 mail.example.com,20 mail2.example.com"
```

### dns:record:delete [#dns-record-delete]

```bash
ymir dns:record:delete [options] <zone> [<record>]
```

Delete DNS record(s) from a DNS zone.

<Callout type="warn" title="Deletes all DNS records without a record ID or filters">

If you don't pass a record ID or any of the `--name`, `--type` or `--value` filters, the `dns:record:delete` command deletes all the DNS records in the DNS zone except the ones managed internally by Ymir. It asks you to confirm twice before doing so. Records that point your mapped domains to your environments aren't internal, so this deletes them too.

</Callout>

The command never deletes internal records, which are SSL certificate validation records and email DKIM records. When you combine filters, a record must match all of them. Ymir requests the deletion of each record separately and deletes it in the background. If a request fails, the command can stop before requesting the remaining deletions, and Ymir doesn't restore records that it already deleted. Save the values of the records before you delete them. See [deleting DNS records][16] for more details.

#### Arguments [#arguments-26]

##### `zone` [#zone-2]

The ID or name of the DNS zone that the DNS record belongs to.

##### `record` [#record-optional]

**optional**

##### `--type=TYPE` [#type-type-dns-record-delete]

Only delete DNS records of this type.

##### `--value=VALUE` [#value-value]

Only delete DNS records with this value. It must match the record's whole value, which is a comma-separated list for records with several values.

### laravel:vapor:migrate [#laravel-vapor-migrate]

```bash
ymir laravel:vapor:migrate
```

Migrate the environment configuration in a Laravel Vapor `vapor.yml` file into the project's `ymir.yml` file. You can only use this command with projects whose `ymir.yml` type is `laravel`, and the `vapor.yml` file must be in the project directory.

The command only changes files in your project directory. It doesn't contact Vapor or change anything on Ymir or your cloud provider, so it doesn't migrate resources, data, environment variables, secrets or DNS.

The command only migrates environments with the same name in both files. It doesn't create environments that only exist in `vapor.yml`, and it leaves environments that only exist in `ymir.yml` unchanged. If no environment names match, the command displays a warning and changes nothing.

For each matching environment, the command copies these `vapor.yml` values into `ymir.yml`, replacing any existing value:

| `vapor.yml` | `ymir.yml` |
| --- | --- |
| `build` | `build.commands` |
| `deploy` | `deployment.commands` |
| `cli-timeout` | `console.timeout` |
| `concurrency` | `website.concurrency` |
| `timeout` | `website.timeout` |
| `database` | `database.server` |
| `database-user` | `database.user` |
| `domain` | `domain` |
| `firewall.bot-control` | `firewall.bots` |
| `firewall.rate-limit` | `firewall.rate_limit` |
| `memory` | `memory` |
| `warm` | `warmup` |
| `scheduler: false` | `cron: false` |
| `runtime` | `architecture` and `php` |
| `queues`, `queue-concurrency`, `queue-memory` and `queue-timeout` | `queues` |

An `-arm` runtime sets `architecture` to `arm64`. A `php-X.Y` runtime sets `php` to `X.Y` and removes an `image` [deployment type][11], so the environment deploys using a zip archive. `queues: false` removes the environment's `queues` configuration. Queue names ending in `.fifo` become FIFO queues, and the `queue-*` values apply to every migrated queue, or to the `default` queue when `vapor.yml` doesn't name any queues. The command ignores all other `vapor.yml` values.

If a matching environment uses the `image` deployment type after the migration, the command asks if you want to create one project-wide `Dockerfile` for all those environments. The default answer, also used in non-interactive mode, is no.

- **No**: for each environment, the command renames an existing `<environment>.Dockerfile` to `<environment>.Dockerfile.bak` and creates a new `<environment>.Dockerfile`. It doesn't change the project-wide `Dockerfile`.
- **Yes**: the command renames the project-wide `Dockerfile` and each environment's `<environment>.Dockerfile` to `.bak` files, and creates a new project-wide `Dockerfile` using the `production` environment, or the first matching environment if there's no `production` environment.

The new Dockerfiles use the same Ymir template as the [`docker:create`][12] command. The PHP version comes from the `laravelphp/vapor` image in the environment's existing `<environment>.Dockerfile`, then the environment's `php` value, then the project type's default PHP version. The architecture comes from the environment's `architecture` value or defaults to `x86_64`.

<Callout type="warn" title="Review the changes before deploying">

Commit or back up your project before running this command, since it can't be undone and has no preview.

- The command rewrites the whole `ymir.yml` file, which doesn't keep its comments or formatting.
- The command saves `ymir.yml` before changing any Dockerfile. If a later step fails, `ymir.yml` stays changed.
- Renaming a Dockerfile overwrites an existing `.bak` file with the same name.
- The new Dockerfiles don't include any custom instructions from your Vapor Dockerfiles. Compare them with the `.bak` files.
- Vapor settings without a mapping above need to be configured by hand.

</Callout>

#### Usage [#usage-laravel-vapor-migrate]

```bash
# Migrate the matching environments in vapor.yml into ymir.yml
ymir laravel:vapor:migrate
```

## Media

Commands to interact with the project media directory.

### media:import [#media-import]

```bash
ymir media:import [options] [<path>]
```

Import files to the environment media directory.

You can only use this command with WordPress, Bedrock and Radicle projects, from your project directory. It uploads every file under `path` to the `uploads` folder of the environment's public S3 bucket, using paths relative to `path`. For example, importing `~/backups/uploads` uploads `~/backups/uploads/2024/05/photo.jpg` as `uploads/2024/05/photo.jpg`. A path that already starts with `uploads/` keeps it, so a file at `~/backups/uploads/uploads/photo.jpg` becomes `uploads/photo.jpg`.

<Callout type="warn" title="Imported files are public">

Anyone can download the files you import. Only import your uploads directory, and never a directory with database exports, backups or private files.

</Callout>

Keep these points in mind:

* **It overwrites files.** A file with the same path replaces the one in the bucket. CloudFront and browsers can keep showing the old file for a while.
* **It isn't a sync.** It doesn't delete files that are in the bucket but not in `path`.
* **It only copies files.** It doesn't add files to the WordPress media library or change URLs in your database.
* **Check the result.** The command can report success even if some uploads failed, and it doesn't retry, resume or verify them. It lists files that it skipped because of a corrupted path. Compare the relative path and size of each local file with the objects under `uploads/` in the bucket, compare the content of important files, and check your site's media URLs.

The `path` can also be an `ftp://` or `sftp://` URL. The Ymir CLI doesn't verify the server's identity, FTP isn't encrypted, and a password in the URL can end up in your shell history. Copy the files to your computer with a tool you trust and import that copy instead.

#### Arguments [#arguments-49]

##### `path` [#path-default-wp-content-uploads-for-wordpress-projects-web-app-uploads-for-bedrock-projects-and-public-content-uploads-for-radicle-projects]

The path to the uploads directory to import. Always pass it. If you don't, the Ymir CLI looks for `/wp-content/uploads` for WordPress projects, `/web/app/uploads` for Bedrock projects or `/public/content/uploads` for Radicle projects at the root of your computer's filesystem, not in your project directory.

#### Options [#options-23]

##### `--environment=ENVIRONMENT` [#environment-environment]

The environment to upload files to. If you don't use this option, the Ymir CLI asks you to choose the environment.

##### `--force` [#force]

Skip the confirmation that importing files overwrites existing files.

##### `--size=SIZE` [#size-size-default-1000]

**default**: `1000`

The number of files to request upload URLs for at a time. Must be at least `1`. It doesn't control how many files upload at once, their size or retries.

#### Usage [#usage-56]

```bash
# Import files to the "staging" environment with a confirmation prompt
ymir media:import --environment=staging ~/backups/uploads

# Import files from your project's uploads directory to the "production" environment
ymir media:import --environment=production wp-content/uploads
```

### provider:delete [#provider-delete]

```bash
ymir provider:delete [<provider>]
```

Delete a cloud provider.

<Callout type="warn" title="Resources aren't deleted on your cloud provider">

The command warns that deleting a cloud provider also deletes all its associated resources on Ymir. They aren't deleted on your cloud provider, so they keep running and AWS keeps billing them. Deleting the connection only removes Ymir's way to manage them. Don't use this command to clean up a project or your AWS account.

</Callout>

Before you delete a connection, delete the projects and team resources that use it, and wait until Ymir has finished deleting them. Deleting the connection first would leave them in your AWS account with no way for Ymir to delete them.

The command asks you to confirm, and the default answer is no. In non-interactive mode, it doesn't delete anything. Ymir doesn't remove the IAM role or access key it used in your AWS account. Delete them in AWS after deleting the connection, once you no longer want Ymir to have access to the account.

#### Arguments [#arguments-64]

## WordPress

Commands to manage WordPress projects.

### wordpress:change-domain [#wordpress-change-domain]

```bash
ymir wordpress:change-domain [<environment> [<domain>]]
```

Change an environment's domain.

<Callout type="info" title="See it in action">

Check out the [video](https://www.youtube.com/watch?v=_cMBIwJcbB8).

</Callout>

The command replaces the current domain with a new one in the environment's WordPress database. The `domain` argument is the current domain. For the new domain, the Ymir CLI uses the environment's mapped domain from your `ymir.yml` file, or asks you to choose or enter one. It uses only the host of both domains, without the scheme or path. If the new domain isn't in your `ymir.yml` file, it offers to add it.

The command then runs `wp search-replace <current-domain> <new-domain> --all-tables` on the environment, followed by `wp cache flush`. It doesn't deploy the environment or change any DNS records.

<Callout type="warn" title="Changes every table without a dry run">

The replacement runs on every table in the database, including tables of other sites that share it, and there's no dry run. Since it replaces the bare domain, it also changes email addresses and longer domains that contain it, such as `shop.example.com` when replacing `example.com`. The cache flush can also clear data of other sites that share your cache cluster, depending on your object cache plugin. Back up the database first. For a reviewed, narrower replacement, run `search-replace` with `--dry-run` using the [`wp`][29] command instead.

</Callout>

#### Arguments [#arguments-68]

##### `environment` [#environment-2]

**optional**

The name of the environment to change the domain of.

##### `domain` [#domain-optional]

**optional**

The current environment domain to replace.

#### Usage [#usage-83]

```bash
# Change an environment's domain with prompt for the environment and the old and new domain
ymir wordpress:change-domain

# Change the "testing" environment's domain with prompt for the old and new domain
ymir wordpress:change-domain testing
```

### wp

```bash
ymir wp [options] [<wp-command>...]
```

Execute a WP-CLI command.

You can only use this command with WordPress, Bedrock and Radicle projects. The WP-CLI command runs on the environment's `console` function. If the WP-CLI command has its own options or quoted values, wrap the whole WP-CLI command in double quotes and use single quotes inside it. Otherwise, the Ymir CLI treats the options as its own.

You can't run `wp shell`, `wp db import` or `wp db export` with this command. Use [`database:import`][30] and [`database:export`][31] instead. Your project's code is read-only on AWS Lambda, so commands that change plugins, themes or WordPress core files, such as `wp plugin update`, don't work. Update them in your project and deploy it.

#### Arguments [#arguments-70]

##### `wp-command` [#wp-command-optional]

**optional**

The WP-CLI command to execute.

#### Options [#options-28]

##### `--environment=ENVIRONMENT` [#environment-environment-2]

The name of the environment to execute the WP-CLI command on. If you don't use this option, the Ymir CLI asks you to choose the environment.

##### `--async` [#async]

Execute WP-CLI command asynchronously.

#### Usage [#usage-85]

```bash
# Run "wp plugin list" with prompt to choose the environment
ymir wp plugin list

# Run "wp plugin list" on the staging environment
ymir wp --environment=staging plugin list

# Run "wp plugin list" on the production environment
ymir wp --environment=production plugin list

# Preview a search and replace on the production environment without changing the database
ymir wp --environment=production "search-replace 'https://old.example.com' 'https://www.example.com' --dry-run"

# Run "wp transient delete --expired" asynchronously on the production environment
ymir wp --environment=production --async "transient delete --expired"
```
